# Архитектурная ревизия Mayori — 10 октября 2026

## Вывод

Текущая структура подходит для дальнейшего развития Mayori как движка креативного текста. Разделение по features, платформенные границы, Cordis lifecycle и журнал DSH дают полезную основу. Переписывать проект или вводить собственный agent loop не требуется.

Главное архитектурное ограничение — общее поведение творческой сессии сейчас принадлежит сценарию чата с персонажем. Создание сессии, персона пользователя, модельный контекст и редактирование связаны с Character Card. Это препятствует письму без карточки и сценариям, где пользователь поручает модели действия нескольких персонажей. Отдельно обнаружен дефект исторического ветвления: изменяемая персона наследуется из текущего snapshot родителя, а не из контекста на точке форка.

Mayori — движок для ролевых игр, отыгрыша, творческого письма и совместного создания историй. Bundle описывает техническую поставку поверх DeepSeek Harness. RPG-механики расширяют движок, но не задают его продуктовую область.

## Объём и метод

Проверены `AGENTS.md`, package exports/files, deployment patch, Host и browser composition roots, архитектурные тесты, session lifecycle, каталоги карточек/персон/пресетов, редактирование и форки, транспорт, Dice/Rules/RollHistory и Compaction. Основное внимание — зависимостям, владельцам состояния, воспроизводимости и соответствию заявленному продуктовому scope.

`pnpm run check` успешно выполняет browser build, синтаксические проверки и **201 тест**. Архитектурные тесты подтверждают отсутствие циклов и запрещённых платформенных импортов, а также полноту поставляемого Host import graph. Зелёные тесты не покрывают все временные границы состояния: это показал отдельный probe наследования персоны.

Для finding 1 выполнен изолированный Node probe с настоящими Mayori Provider/Store и временным каталогом; Cordis/Agent boundary замещён минимальным контекстом. Остальные findings основаны на чтении реализации и существующих тестов. Это не полная проверка запущенного приложения: browser smoke и установка в временный DSH profile в рамках ревизии не выполнялись. Runtime и deployment-композиция не изменены.

## Что уже сделано правильно

- `src/host/application.js` и `src/client/plugin.js` владеют сборкой. Feature-модули не импортируют composition roots; Host и browser отделены, domain/shared не используют платформенные SDK. Эти границы проверяются `test/architecture.test.js`.
- Session history, fork, maintenance, tool results и prompt sections используют DSH. Отдельный конкурирующий движок истории и патчи `agent-loop` не нужны.
- Пресеты отделяют пользовательский каталог от снимка выбора в сессии. `LoggedSessionPresetProvider` восстанавливает инструкции из собственного унаследованного журнала, а не из текущего default или родительского каталога.
- Dice использует настоящий источник случайности; Rules потребляет Dice. RollHistory читает записанные результаты и не бросает заново. Версионированные readers не пересчитывают историю по текущей конфигурации.
- Compaction использует штатный engine seam и сохраняет настройки в журнале; DSH владеет диапазоном и заменой model surface.
- Каталоги ресурсов принадлежат Host. Browser хранит настройки представления и черновики, а не единственную копию канонического состояния.
- Сервисы, slots, стили и prompt bindings регистрируются через Cordis ownership. Для публичных package entry points есть проверки поставки.

## Findings

Приоритет **P1** означает исправление перед расширением сценариев; **P2** — следующий архитектурный этап. Продуктовые ограничения ниже не объявляются случайными регрессиями: часть из них соответствует первому реализованному срезу.

### 1. P1 — исторический форк наследует текущую персону родителя

**Код:** [Character Session Provider](../src/features/character-session/host/provider.js), `_restore` и `setPersona`; [selection store](../src/features/character-session/host/store.js), `update`.

`setPersona` перезаписывает один файл выбора сессии. `_restore` для нового дочернего чата читает этот файл по `parentSession` и копирует его целиком. Точка наследования журнала и прежний model-visible context не учитываются.

**Воспроизведение:** сохранить персону `Before`, затем заменить родительский snapshot на `After`; создать дочерний Agent с `parentSession` и префиксом до изменения. `_restore` сохраняет дочерней сессии `After` и регистрирует её в prompt. Probe получил:

```json
{"forkInheritedEventCount":10,"personaAtFork":"Before","restoredPersona":"After","inheritedLogReads":0}
```

Probe проверяет сам путь восстановления Provider, а не весь native fork end-to-end. Код не читает префикс вообще, поэтому не может различить ветки до и после смены персоны. Существующий тест форка проверяет копирование ID карточки, но не изменение персоны после точки ветвления.

**Последствие:** редактирование старой реплики или форк раннего места после смены персоны может продолжить историю с другим участником/описанием. Исторические запросы не переписываются, но новый запрос ветки получает контекст, отсутствовавший на её точке происхождения.

**Рекомендация:** логировать явные изменения session context через стандартный DSH snapshot seam и восстанавливать их из собственного унаследованного префикса. Файл текущей проекции допустим как cache/read model, но не как источник контекста исторического форка. Для старых сессий нужен явно описанный fallback без выдуманного исторического выбора. Учесть также ветку ручного приветствия без унаследованного префикса — она уже переносит preset snapshot и должна переносить нужный session context.

**Проверка исправления:** форки до/после смены персоны, редактирование раннего сообщения, resume обеих веток, удалённая исходная карточка/персона; сравнить model context и UI persona. Смена в одной ветке не должна менять другую.

### 2. P1 — создание и редактирование общей сессии зависят от карточки

**Код:** [startCharacterSession](../src/features/character-session/client/start.js); [home](../src/client/shell/home.jsx), `HomeConversation`; [sidebar](../src/client/shell/sidebar.jsx); [Message Revision Provider](../src/features/message-revisions/host/provider.js), `_target`.

Основной путь создания требует карточку. Sidebar исключает New Session; безымянный пустой чат показывает Home вместо редактора. Даже если обычная сессия создана средствами DSH, `_target` требует `characters.state(...).character` и отклоняет редактирование без выбранного персонажа.

**Последствие:** пользователь не получает штатного пути «начать текст с нуля»; общая возможность редактировать/ветвить текст искусственно принадлежит character chat. Каталог пресетов сам по себе не снимает эти ограничения.

**Рекомендация:** выделить `creative-session` как владельца общего создания и session context. Provider должен делегировать lifecycle штатным DSH services, Consumer — дать вход с главной. Character Session добавляет опциональную карточку и authored opening. Message Revisions работает с обычным журналом; special-case приветствия остаётся расширением character feature.

**Проверка исправления:** создать, назвать, открыть и продолжить сессию без карточки; редактировать реплики, повторить ответ и возобновить ветку после перезапуска. Старые character chats сохраняют текущий формат и поведение.

### 3. P2 — ролевая политика закреплена в общем контексте

**Код:** [application](../src/host/application.js), начальный preset; [director](../src/host/director.js); [character context](../src/features/character-session/domain/character.js), `buildCharacterContext`; [preset codec](../src/features/presets/shared/preset.js), `presetContext`.

Стартовая инструкция объявляет Mayori game master. Character context всегда задаёт активного NPC, игрока и запрет выбирать мысли/реплики/действия персонажа пользователя. Обёртка любого пресета также называет его role-playing instructions. Пользователь может написать другой preset, но независимый character context продолжает задавать строгую ролевую политику.

**Последствие:** просьба написать диалог нескольких героев или продолжить авторскую сцену конфликтует с модельной рамкой, рассчитанной на отдельного player-controlled персонажа.

**Рекомендация:** общую цель и границы авторства задавать пользовательскими инструкциями и явным session snapshot. Ролевой сценарий сохраняет строгую player agency по умолчанию; авторский сценарий позволяет явно делегировать действия и реплики. Не ограничивать продукт фиксированным набором режимов и не делать prompt единственным хранилищем выбора. Технические имена экспортов, сервисов и старых markers менять только с совместимыми readers.

**Проверка исправления:** запросы на roleplay и на авторский текст дают соответствующий контекст; явное делегирование сохраняется при resume/fork; старые журналы читаются без миграции названий markers.

### 4. P2 — переключение optional capabilities не восстанавливает прежнюю композицию при ошибке

**Код:** [application](../src/host/application.js), `registerOptionalPlugins`; [Plugin Settings Provider](../src/features/plugins/host/provider.js), `refresh`.

Reconcile сначала выгружает все предыдущие mounts, а затем последовательно создаёт новую композицию. При ошибке любого mount откат отсутствует: предыдущий рабочий набор уже снят, часть нового может быть активна. Settings Provider оставляет прежний `active` и записывает ошибку, поэтому `active` больше не гарантирует соответствие фактическим tools. Повторный refresh может восстановить состояние, но не устраняет промежуточную рассогласованность.

**Последствие:** неудачное изменение capabilities способно убрать ранее работавшие инструменты, а UI сообщает предыдущий активный набор с ошибкой. Это особенно существенно для пользовательских Rules profiles и внешних providers.

**Рекомендация:** сначала валидировать зависимости и deployment config без снятия рабочего набора; при ошибке активации освобождать частичные mounts и восстанавливать последнюю успешную композицию. Если откат тоже не удался, публиковать фактическое деградированное состояние. Сохранить запрет изменения tools посреди текущего ответа.

**Проверка исправления:** инъекция ошибки на каждом этапе mount; после отказа прежние tools остаются доступны либо UI точно показывает фактический отказ. Повтор и unload не оставляют частичных providers/listeners.

### 5. P2 — допустимое развёртывание RPC жёстко ограничено loopback

**Код:** [HTTP boundary](../src/host/transport/http.js), `isLoopbackRequest`; [deployment patch](../cordis.patch.yml), настройки `webserver` и `web-runtime`; [route tests](../test/host/routes.test.js).

RPC требует loopback hostname в Host и совпадение Origin. При этом deployment patch передаёт `host`, `publicUrl`, TLS и `trustedHosts` штатного Web runtime. Даже корректный same-origin запрос с разрешённого публичного или LAN hostname отвергается; тесты явно фиксируют отказ для `example.com`.

**Последствие:** доступная Web-оболочка не гарантирует работу Mayori catalog/session endpoints за reverse proxy или при доступе с другого устройства. Для локального приложения такая граница допустима; это ограничение deployment, а не обнаруженная уязвимость.

**Рекомендация:** явно документировать локальную границу. Если нужен сетевой доступ, добавить валидируемую deployment policy через поддерживаемые Web auth/origin contracts DSH. Простое удаление проверки Host без проверки доверия не является исправлением.

**Проверка исправления:** разрешённый origin, запрещённый origin, запросы без Origin, reverse proxy и unload; локальная изоляция сохраняется при default Config.

### 6. P2 — каталог целиком загружает карточки и PNG для каждого чтения

**Код:** [Character Library Store](../src/features/characters/host/store.js), `list` и `#readRecord`; [Character Session Provider](../src/features/character-session/host/provider.js), `create` и `_selectWhileIdle`.

`list()` параллельно читает все JSON и PNG, превращает изображения в base64 и возвращает полные карточки. Создание одного чата тоже вызывает `library.list()` для поиска ID. UI pagination ограничивает отображаемые карточки, но не I/O, размер ответа или память Host/browser. Ошибка чтения одного JSON отклоняет весь `Promise.all` и делает весь каталог недоступным.

**Последствие:** рост библиотеки повышает стоимость открытия галереи и запуска одного чата. Одна повреждённая карточка блокирует здоровые ресурсы. Это подтверждённая структура I/O; количественные пределы производительности не измерялись.

**Рекомендация:** добавить узкий lookup по ID и лёгкий listing metadata с Host pagination; изображения и полные card payloads получать по необходимости. Изолировать повреждённые записи с диагностикой по ресурсу. Начать с lookup, не вводя отдельную базу данных без измерений.

**Проверка исправления:** создать чат по ID без чтения других карточек/PNG; повреждённая соседняя карточка не блокирует lookup; измерить библиотеку реалистичного размера и проверить lazy загрузку изображений.

## Целевая декомпозиция

Сохраняется один пакет с существующими платформенными слоями и composition roots. Возможный следующий ownership:

| Область | Ответственность |
| --- | --- |
| `creative-session` | Создание общей сессии, явный выбор инструкций/границ авторства, журналируемый context и его восстановление на точке ветвления |
| `presets` | Каталог пользовательских инструкций и сохранённый выбор сессии; продолжить существующий seam |
| `character-session` | Привязка карточки, выбранное приветствие и character-specific context поверх общей сессии |
| `characters`, `personas` | Каталоги ресурсов; выбор в сессии отделён от текущего содержимого каталога |
| `message-revisions`, `history`, `trajectory`, `compaction` | Общие возможности творческих сессий с узкими расширениями для character chat |
| `dice`, `rules`, `roll-history` | Опциональные механики; сессия должна работать при их отключении |
| Будущий story/campaign journal | Подтверждённый канон и проекции между сессиями; model-visible snapshot принадлежит session log |

Это распределение владельцев, не требование сразу переносить все файлы. Новые seams должны включать Service Definition, Provider и Consumer. Собственные события истории, универсальный framework и второй цикл Agent не нужны.

Сейчас каталоги карточек/персон/пресетов — ресурсы; session log — история фактически переданного модели контекста; selection files — отдельные текущие snapshots. Будущий журнал канона должен иметь своего владельца и не подменять ни каталог ресурсов, ни session history. Его необходимость зависит от сценария: для свободного письма не требуется обязательная RPG-кампания.

## Порядок работ

1. Исправить historical fork context и добавить временные сценарии в тесты. Это условие безопасного расширения ветвления.
2. Реализовать минимальную сессию без карточки и отвязать общее редактирование от Character Session. Проверить реальный DSH profile и browser flow.
3. Ввести явные границы авторства, обновить начальные presets и framing без переписывания старых пользовательских presets/logs.
4. Сделать отказ переключения capabilities согласованным с фактической композицией.
5. Добавить lookup карточек, затем измерить потребность в лёгком listing/pagination. Решение о сетевом deployment принимать как отдельную продуктовую возможность.
6. Добавлять долговечный story/campaign canon и конкретные rulesets по необходимости поверх общего ядра.

Каждое изменение поведения сопровождается тестами и affected guide. Для composition changes дополнительно устанавливать checkout во временный DSH profile и проверять `--dump-config`.

## Что изменено этой ревизией

Последующее исполнение performance-задачи: добавлены прямой lookup, постраничный SQLite listing, медиа по content hash с миниатюрами, ограниченные кеши превью и неактивных browser providers. Измерения и ограничения — [performance guide](performance.md). Остальные findings этой ревизии сохраняют силу; описание ниже относится к исходному этапу документирования.

Исправлено позиционирование в `AGENTS.md`, `README.md`, `package.json`, `docs/architecture.md` и `docs/roadmap.md`; этот документ сохраняет результаты ревизии. В правилах разработки состояние и пользовательский контроль расширены до творческих сценариев. Целевые возможности отделены от уже реализованных. Runtime prompts, providers, exports, deployment patch и форматы пользовательских данных не изменены. Findings выше остаются задачами реализации.
